# Advanced Evaluation

이 Skill은 여러 Open LLM이 동일한 질문에 생성한 실제 답변을 공정하게 평가하고,
모델별 점수, 장단점, 최종 순위, 판정 근거와 신뢰도가 포함된 Markdown 보고서를 생성하기 위해 사용한다.

다음과 같은 다양한 질문을 평가할 수 있다.

- 개념 설명
- 사실 확인
- 기술 및 코드
- 분석 및 추천
- 요약 및 변환
- 창작 및 아이디어
- 절차 및 문제 해결

답변 길이, 모델 인지도, 제공 기업, 응답 순서만으로 우수한 모델을 판단하지 않는다.

---

## 적용 조건

다음 요청에는 이 Skill을 사용한다.

- 여러 모델의 답변을 비교해 달라는 요청
- 랜덤 모델 2~4개의 답변을 평가해 달라는 요청
- 사용자가 지정한 모델들의 답변을 비교해 달라는 요청
- 모델별 점수, 순위, 장단점 또는 최종 승자를 요구하는 요청
- Open LLM 비교 결과를 Markdown 보고서로 저장하는 요청

다음 요청에는 사용하지 않는다.

- 단일 모델에 일반 답변만 요청하는 경우
- 실제 모델 호출 없이 예상 성능만 비교하는 경우
- 모델 비교 없이 파일만 작성하거나 수정하는 경우
- UI 디자인이나 문서 스타일만 요청하는 경우
- 모델 평가가 필요하지 않은 일반 작업

---

## 필요한 도구

전체 평가 프로세스에는 다음 도구가 필요하다.

- `save_open_llm_report`: 여러 모델을 실제 호출하고 원문 보고서를 저장
- `read_file`: 생성된 보고서와 모델별 원문 답변 확인
- `write_file` 또는 `edit_file`: 평가 결과를 보고서에 반영
- `web_search`: 사실 검증이 필요하고 도구가 제공되는 경우에만 선택적으로 사용

필요한 도구가 제공되지 않으면 모델을 호출하거나 평가하거나 보고서를 저장했다고 주장하지 않는다.

## 핵심 원칙

### 실제 응답만 평가

모델의 알려진 성능이나 평판을 근거로 비교하지 않는다.

반드시 `save_open_llm_report`가 실제로 생성한 모델 답변만 평가한다.

### 모든 모델에 동일한 조건 적용

모든 후보 모델에는 다음 조건을 동일하게 적용한다.

- 동일한 사용자 질문
- 동일한 언어 요구사항
- 동일한 최대 출력 길이
- 가능한 범위에서 동일한 temperature
- 동일한 시스템 지침

모델마다 질문을 다르게 재작성하지 않는다.

### 원문 답변 보존

모델별 실제 답변 원문은 수정, 요약, 교정하거나 다시 작성하지 않는다.

평가 내용은 원문과 구분된 별도 섹션에 작성한다.

### 평가 중 모델 신원 숨기기

평가 중에는 모델 ID와 제공 기업을 판단 근거로 사용하지 않는다.

정상 응답을 다음과 같이 임시 익명화한다.

- 응답 A
- 응답 B
- 응답 C
- 응답 D

모든 평가가 완료된 후에만 익명 응답을 실제 모델 ID와 다시 연결한다.

### 속도와 품질 분리

응답 시간은 운영 성능 지표이며 답변 품질 점수가 아니다.

사용자가 명시적으로 효율성 비교를 요청하지 않았다면 다음 항목을 품질 점수에 포함하지 않는다.

- 응답 속도
- 답변 길이
- 모델 크기
- 기업 인지도
- API 제공자 평판
- 모델 인기도

응답 시간은 별도의 실행 성능 항목으로만 보고한다.

### 동률 허용

품질 차이가 명확하지 않으면 억지로 승자를 만들지 않는다.

다음 경우 동률 또는 낮은 신뢰도로 표시한다.

- 평가 근거가 부족한 경우
- 위치를 교환한 Pairwise 결과가 일치하지 않는 경우
- 최종 점수 차이가 매우 작은 경우
- 질문 자체가 주관적인 경우

## 프로세스: 반드시 따라야 할 단계

### 1단계: 비교 요청 해석

사용자 요청에서 다음 정보를 추출한다.

- 비교 질문
- 비교할 모델 수
- 랜덤 선택 여부
- 지정 모델 또는 모델 계열
- Markdown 보고서 저장 여부
- 사용자가 별도로 지정한 평가 기준

사용자가 평가 기준을 지정했다면 기본 기준보다 우선 적용한다.

랜덤 모델 요청은 다음 형식으로 정규화한다.

```text
질문: <모든 모델에 전달할 동일한 질문>
선택: random:<2~4>
```

지정 모델 요청은 다음 형식으로 정규화한다.

```text
질문: <모든 모델에 전달할 동일한 질문>
선택: models:<쉼표로 구분한 모델명 또는 모델 ID>
```

`질문`과 `선택` 필드명은 현재 `save_open_llm_report` 도구 계약이므로 변경하지 않는다.

### 2단계: 실제 모델 비교 실행

`save_open_llm_report`를 정확히 한 번 호출한다.

다음 행동은 하지 않는다.

- 모델마다 도구를 나누어 호출
- 동일한 비교 요청을 반복 실행
- 실패한 모델의 답변을 직접 생성
- 지원하지 않는 모델을 임의로 다른 모델로 교체

도구 반환값에서 다음 정보를 확인한다.

- `status`
- `report_path`
- `success_count`
- `failure_count`
- 실제 선택 모델
- 지원하지 않는 요청 모델

도구가 실패하면 평가 결과를 임의로 생성하지 않고 실패 원인을 사용자에게 알린다.

### 3단계: 생성된 보고서 읽기

도구가 반환한 `report_path`를 사용하여 `read_file`로 보고서 전체를 읽는다.

다음 내용을 추출한다.

- 원래 비교 질문
- 모델 ID
- 모델 계열
- 실행 상태
- 응답 시간
- 모델별 실제 답변 원문
- 실패 원인

정상 응답을 생성한 모델만 평가하고 순위를 부여한다.

정상 응답이 2개 미만이면 비교 순위를 생성하지 않는다.

### 4단계: 모델 답변 익명화

정상 응답에 익명 라벨을 부여한다.

```text
응답 A -> 실제 모델 정보 비공개
응답 B -> 실제 모델 정보 비공개
응답 C -> 실제 모델 정보 비공개
응답 D -> 실제 모델 정보 비공개
```

평가 중에는 다음 정보를 사용하지 않는다.

- 모델 ID
- 모델 제공 기업
- 알려진 모델 평판
- 응답 속도
- 답변 길이

직접 점수 평가와 Pairwise 평가가 모두 끝난 뒤 실제 모델명을 다시 연결한다.

### 5단계: 질문 유형별 평가 루브릭 생성

사용자 질문을 다음 유형 중 가장 가까운 하나로 분류한다.

- 사실 및 개념 설명
- 기술 및 코드
- 분석 및 추천
- 요약 및 변환
- 창작 및 아이디어
- 절차 및 문제 해결

평가 기준은 최대 5개만 사용한다.

하나의 평가 기준은 하나의 명확한 품질 요소만 측정해야 한다.

전체 가중치 합은 반드시 100이어야 한다.

### 6단계: 모델별 직접 점수 평가

각 익명 응답을 다른 응답과 비교하기 전에 독립적으로 평가한다.

선택한 루브릭을 사용하여 각 기준에 1점부터 5점까지 부여한다.

각 점수에는 답변에서 확인할 수 있는 간결한 근거를 포함한다.

직접 평가 점수는 0점부터 100점 사이로 계산한다.

### 7단계: Pairwise 비교

정상 응답의 모든 조합을 Pairwise 방식으로 비교한다.

각 조합은 답변 위치를 바꾸어 두 번 평가한다.

다음 내용을 기록한다.

- 1차 비교 결과
- 위치 교환 결과
- 최종 판정
- 판정 신뢰도

두 평가 결과가 일치하지 않으면 동률로 처리한다.

### 8단계: 최종 점수 및 순위 계산

다음 결과를 결합한다.

- 직접 평가 점수
- Pairwise 점수

최종 점수를 계산하고 정상 응답 모델의 순위를 결정한다.

근거가 부족하면 사실상 동률을 허용한다.

### 9단계: Markdown 보고서 보강

기존 보고서의 실제 모델 답변과 실행 정보를 그대로 보존한다.

다음 내용을 추가한다.

- 평가 설계
- 평가 루브릭
- 모델별 직접 점수
- Pairwise 결과
- 최종 순위
- 모델별 장단점
- 판정 신뢰도
- 실행 성능
- 평가 한계

완성된 보고서를 동일한 `report_path`에 저장한다.

### 10단계: 사용자에게 완료 결과 전달

사용자에게 다음 정보만 간결하게 전달한다.

- 정상 비교 모델 수
- 최종 1위 또는 동률 여부
- 판정 신뢰도
- Markdown 보고서 저장 경로
- 실패 모델 또는 검증 한계

전체 모델 답변과 긴 평가표를 채팅에 반복해서 출력하지 않는다.

## 직접 점수 평가

각 익명 응답을 독립적으로 평가한다.

각 평가 기준은 1점부터 5점까지 사용한다.

| 점수 | 의미 |
|---:|---|
| 1 | 핵심 요구를 충족하지 못하거나 중대한 오류가 있음 |
| 2 | 일부 내용은 맞지만 중요한 오류나 누락이 많음 |
| 3 | 기본 요구를 충족하지만 개선할 부분이 분명함 |
| 4 | 정확하고 유용하며 작은 약점만 있음 |
| 5 | 요청을 매우 잘 충족하고 의미 있는 오류나 불필요한 내용이 거의 없음 |

각 기준 점수에는 다음 내용을 포함한다.

- 답변에서 확인되는 구체적인 근거
- 부족하거나 잘못된 부분
- 한 문장으로 정리한 개선 방향

내부 추론 과정 전체를 출력하지 않는다.

보고서에는 짧고 검증 가능한 평가 근거만 작성한다.

직접 평가 점수는 다음 공식으로 계산한다.

```text
직접 평가 점수 = Σ((기준별 점수 / 5) × 기준별 가중치)
```

결과 범위는 0점부터 100점이다.

## 사실 검증

사실 정확성이 중요한 질문은 다음 순서로 검증한다.

1. 사용자 질문에 정답 또는 기준 자료가 포함됐는지 확인한다.
2. 기준 자료가 있다면 모든 모델을 동일한 자료에 대조한다.
3. 최신 정보나 외부 검증 가능한 사실이 중요하고 `web_search`가 제공되면 최소한의 공신력 있는 자료를 확인한다.
4. 동일한 검증 근거를 모든 모델에 적용한다.
5. 검증 수단이 없으면 사실 정확성 미검증이라고 명시한다.

검증하지 않은 사실을 확정된 정답으로 표현하지 않는다.

외부 자료를 사용했다면 보고서에 자료명과 URL을 기록한다.

모델마다 서로 다른 검증 기준을 적용하지 않는다.

## Pairwise 비교

직접 점수 평가 후 정상 응답의 모든 조합을 비교한다.

모델이 2개라면 비교 조합은 1개다.

```text
A-B
```

모델이 3개라면 비교 조합은 3개다.

```text
A-B
A-C
B-C
```

모델이 4개라면 비교 조합은 6개다.

```text
A-B
A-C
A-D
B-C
B-D
C-D
```

각 조합은 위치 편향을 줄이기 위해 두 번 평가한다.

```text
1차: 응답 A -> 응답 B
2차: 응답 B -> 응답 A
```

두 평가에서 실제로 동일한 응답이 승리하면 해당 응답의 승리로 처리한다.

두 평가 결과가 일치하지 않으면 동률로 처리하고 신뢰도를 낮춘다.

다음 편향을 방지한다.

- 먼저 제시된 응답 선호
- 긴 응답 선호
- 자신감 있는 문체 선호
- 특정 모델이나 기업 선호
- 평가 모델과 같은 계열의 답변 선호
- 불필요한 전문용어가 많은 답변 선호
- 내용보다 Markdown 형식이 좋은 답변 선호

각 Pairwise 결과는 다음과 같이 기록한다.

- 승리: 1점
- 동률: 0.5점
- 패배: 0점

Pairwise 점수는 다음 공식으로 계산한다.

```text
Pairwise 점수 =
(승리 수 + 0.5 × 동률 수) / 전체 대결 수 × 100
```

## 최종 점수 및 순위

기본 최종 점수는 다음 공식으로 계산한다.

```text
최종 점수 = 직접 평가 점수 × 0.7 + Pairwise 점수 × 0.3
```

최종 점수는 소수점 첫째 자리까지 표시한다.

사용자가 속도 또는 비용 평가를 명시적으로 요청하지 않았다면 응답 속도를 품질 점수에 포함하지 않는다.

효율성 평가가 필요한 경우에도 품질 점수와 별도 항목으로 보고한다.

다음 조건을 모두 만족하면 사실상 동률로 표시할 수 있다.

- 최종 점수 차이가 3점 미만
- 위치 교환 Pairwise 결과가 일치하지 않음
- 품질 차이를 설명할 충분한 근거가 없음

동률이어도 모델별 강점과 약점은 각각 작성한다.

실패 모델에는 점수나 순위를 부여하지 않는다.

## 판정 신뢰도

최종 판정에는 반드시 신뢰도를 포함한다.

### 높음

다음 조건에 해당하면 높은 신뢰도로 표시한다.

- 위치 교환 Pairwise 결과가 일관됨
- 평가 기준이 명확함
- 검증 자료 또는 명확한 정답이 있음
- 모델 간 품질 차이가 뚜렷함

### 보통

다음 조건에 해당하면 보통 신뢰도로 표시한다.

- Pairwise 결과가 대부분 일관됨
- 사실 정확성을 완전히 검증하지 못함
- 일부 평가 기준이 주관적임
- 모델 간 차이는 있지만 크지 않음

### 낮음

다음 조건에 해당하면 낮은 신뢰도로 표시한다.

- 위치 교환 결과가 반복해서 달라짐
- 정답이나 검증 자료가 없음
- 모델 간 점수 차이가 매우 작음
- 사용자 질문이 모호함
- 정상 응답 모델 수가 부족함

신뢰도가 낮으면 단일 승자를 확정하지 않고 동률 또는 잠정 순위로 표현한다.

## 보고서 저장 절차

1. `save_open_llm_report`가 생성한 보고서 전체를 `read_file`로 읽는다.
2. 모든 모델의 원문 답변과 실행 정보를 그대로 보존한다.
3. 평가 섹션을 포함한 완전한 Markdown 문서를 작성한다.
4. 동일한 `report_path`에 `write_file`로 한 번 저장한다.
5. 파일 저장 결과가 성공인지 확인한다.
6. 저장에 실패하면 평가 보고서가 완성됐다고 주장하지 않는다.

원본 보고서를 읽지 않은 상태에서 기존 파일을 덮어쓰지 않는다.

사용자가 별도 파일을 요청하지 않았다면 두 번째 보고서를 만들지 않는다.

## 실패 및 예외 처리

### 일부 모델만 실패한 경우

- 성공한 모델만 평가한다.
- 실패 모델은 순위에서 제외한다.
- 실패 원인을 보고서에 기록한다.

### 정상 응답이 1개인 경우

- 비교 순위를 생성하지 않는다.
- 단일 응답 평가만 제공한다.
- 비교할 수 없는 이유를 명시한다.

### 모든 모델이 실패한 경우

- 점수와 승자를 생성하지 않는다.
- API 또는 모델 호출 실패 내용만 보고한다.

### 지정 모델을 지원하지 않는 경우

- 임의의 다른 모델로 교체하지 않는다.
- 지원하지 않는 모델명을 보고한다.
- 정상 호출된 지정 모델만 평가한다.

### 보고서 읽기에 실패한 경우

- 누락된 보고서를 임의로 복원하지 않는다.
- 파일 경로와 읽기 실패 원인을 반환한다.

### 보고서 저장에 실패한 경우

- 실패한 파일 경로와 오류를 알린다.
- 보고서가 정상 저장됐다고 응답하지 않는다.

### 사실 검증을 수행할 수 없는 경우

- 지시 준수, 완전성, 명확성, 내부 일관성과 같이 확인 가능한 기준으로 평가를 계속한다.
- 사실 정확성은 미검증으로 표시한다.
- 사실 정확성이 핵심인 질문이라면 판정 신뢰도를 낮춘다.

## 사용 예시

### 예시 1: 랜덤 모델 2개 비교

**사용자 요청:**

```text
"프롬프트 인젝션이 무엇인지 한 문장으로 설명해줘"라는 질문으로 랜덤 모델 2개를 비교하고 Markdown 보고서로 저장해줘.
```

**예상 동작:**

1. `advanced-evaluation` Skill을 로드한다.
2. 다음 형식으로 요청을 정규화한다.

```text
질문: 프롬프트 인젝션이 무엇인지 한 문장으로 설명해줘.
선택: random:2
```

3. `save_open_llm_report`를 한 번 호출한다.
4. 생성된 보고서를 읽는다.
5. 정상 응답만 평가 대상으로 선택한다.
6. 두 응답을 응답 A와 응답 B로 익명화한다.
7. 간결한 개념 설명에 맞는 평가 기준을 선택한다.
8. 모델별 직접 점수를 계산한다.
9. A-B와 B-A 순서로 Pairwise 비교한다.
10. 점수, 근거, 순위, 신뢰도를 Markdown 보고서에 추가한다.
11. 최종 1위 또는 동률 여부와 보고서 경로를 반환한다.

**사용자 요청:**

```text
"프롬프트 인젝션이 무엇이고 RAG 시스템에서 왜 위험한지 설명해줘"라는 질문으로 랜덤 모델 4개를 비교하고 Markdown 보고서로 저장해줘.
```

## 가이드라인

### 평가 근거

- 모든 점수는 답변에서 관찰할 수 있는 내용에 근거한다.
- 평가 근거는 간결하고 구체적으로 작성한다.
- 사실 오류와 단순한 내용 누락을 구분한다.
- 문체 선호와 객관적인 품질 차이를 구분한다.
- 근거 없는 정밀한 숫자를 만들지 않는다.

### 평가 루브릭

- 하나의 기준은 하나의 품질 요소만 측정한다.
- 평가 기준은 최대 5개로 제한한다.
- 전체 가중치 합은 100으로 맞춘다.
- 사용자 질문 유형에 맞게 기준을 조정한다.
- 사용자가 평가 기준을 제공했다면 우선 적용한다.

### 편향 완화

- 평가 중 모델 신원을 숨긴다.
- 모든 Pairwise 조합에서 답변 순서를 바꾼다.
- 불필요하게 긴 답변에 추가 점수를 주지 않는다.
- 정확하지 않은 자신감 있는 표현을 높게 평가하지 않는다.
- 동률을 허용한다.
- 판정 불확실성을 보고한다.

### 보고서 품질

- 실제 모델 원문을 그대로 보존한다.
- 품질 지표와 실행 성능 지표를 분리한다.
- 모든 순위에 평가 근거를 포함한다.
- 실패 모델과 평가 한계를 기록한다.
- 최종 결론과 점수표가 서로 일치해야 한다.

### 도구 사용

- 한 비교 요청에서 `save_open_llm_report`를 한 번만 호출한다.
- 보고서를 수정하기 전에 반드시 읽는다.
- 평가가 완료된 후에만 보강된 보고서를 저장한다.
- 파일 저장 결과를 확인한다.
- 제공되지 않은 도구를 사용했다고 주장하지 않는다.

작업 완료 후 다음 내용을 간결하게 전달한다.

- 최종 1위 또는 사실상 동률
- 판정 신뢰도
- Markdown 보고서 저장 경로
- 실패 모델 수
- 중요한 검증 한계

채팅에 모든 모델의 전체 답변이나 전체 평가표를 반복해서 출력하지 않는다.

상세 내용은 저장된 Markdown 보고서에서 확인하도록 안내한다.

## 금지 사항

- 실제 호출하지 않은 모델의 답변 생성
- 모델 이름만 보고 점수 부여
- 가장 긴 답변을 자동으로 우승 처리
- 가장 빠른 모델을 자동으로 우승 처리
- 실패 모델에 점수 부여
- 근거 없는 소수점 점수 생성
- 위치 교환 없이 한 번만 Pairwise 비교
- 실제 모델 원문 수정
- 검증 없이 사실 정확성을 확정
- 모델마다 서로 다른 평가 기준 적용
- 모델 호출 실패 내역 숨기기
- 지원하지 않는 모델을 임의로 교체
- 작은 점수 차이를 과도하게 해석
- 보고서 저장 실패 후 완료됐다고 응답
